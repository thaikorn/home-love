## 1. แต้มไม่ตรงกัน

### 1.1 โบนัสภารกิจประจำวันไม่เคยถูกจ่าย (ต้นเหตุหลัก)

`parent.approve` เดิมเรียงลำดับแบบนี้:

```
คิดแต้ม → แจกแต้ม + เช็คภารกิจประจำวัน → คิดดาเมจบอส → ค่อยปั๊มสถานะ "ผ่าน" ลงชีต
```

ตอน `awardDailyQuest_()` ไปนับว่า "วันนี้ทำงานผ่านกี่ชิ้นแล้ว" งานชิ้นที่กำลังอนุมัติอยู่
ยังเป็น **"รอตรวจ"** ในชีต จึงนับขาดไป 1 ชิ้นเสมอ

ผลกับเป้าเริ่มต้น (วันละ 3 ชิ้น, โบนัส 20):

| เด็กทำได้ | หน้าจอเด็กแสดง | โบนัสที่ได้จริง |
|---|---|---|
| 3 ชิ้น | `3/3` เต็มหลอด | **0** — ไม่มีวันได้ |
| 4 ชิ้น | `3/3` | 20 (ช้าไป 1 ชิ้น) |

เด็กที่ทำพอดีวันละ 3 ชิ้นจึงเห็นหลอดเต็มแต่แต้มไม่เข้า — นี่คืออาการ "ไม่ตรงกัน" ที่เห็นชัดที่สุด
ด้วยเหตุผลเดียวกัน **ดาเมจบอสก็ตกงานชิ้นล่าสุดไปทุกครั้ง**

**แก้:** ปั๊มสถานะ `ผ่าน` ลงชีตก่อนเข้าลูปแจกแต้ม แล้วเขียนคอลัมน์ `awards`
(ยอดรายคนที่รวมโบนัสสตรีคแล้ว) ก่อนคิดดาเมจบอส

### 1.2 โบนัสภารกิจ/บอส เข้ากระเป๋าแต่ไม่เข้า XP

แต้มโบนัสถูกบันทึกใน tab `Quests` และบวกเข้า `Children.points` ผ่าน `addPoints_`
แต่ `childXp_()` อ่านแค่ `Submissions` + `PointAdjustments` ฝั่งบวก **ไม่เคยอ่าน `Quests`**

ผลคือหน้าผู้ปกครองโชว์ "XP รวม" น้อยกว่า "แต้มที่มี" ทั้งที่เด็กยังไม่ได้แลกอะไรเลย
และเลเวลขึ้นช้ากว่าที่ควร

**แก้:** `childXp_()` นับแต้มใน `Quests` ด้วย · `periodPointsByChild_()` (กระดานผู้นำ + ดาเมจบอส)
นับเฉพาะ `kind = 'daily'` — **รางวัลจากการล้มบอสห้ามนับเป็นดาเมจ** ไม่งั้นล้มตัวหนึ่งแล้ว
รางวัลจะไหลไปฟาดตัวถัดไปเองเป็นลูกโซ่

### 1.3 อธิบายส่วนต่างบนหน้าจอ

"แต้มที่มี" กับ "XP รวม" **ต่างกันได้ตามการออกแบบ** (แลกของรางวัลแล้วเลเวลต้องไม่ลด)
แต่เดิมวางสองเลขไว้ข้างกันเฉยๆ ดูเผินๆ เหมือนระบบคิดผิด

หน้าแต้มของผู้ปกครองจึงเพิ่มบรรทัด `หามาได้ทั้งหมด N (XP) · ใช้ไปแล้ว M · เหลือ K`
ให้เลขสองตัวกระทบยอดกันได้ในบรรทัดเดียว

### ค่าคงที่ควรรู้

```
แต้มที่มี = XP − (แลกของรางวัล + ปรับแต้มฝั่งลบ)
XP        = งานที่ผ่าน + ปรับแต้มฝั่งบวก + โบนัสภารกิจ/บอส
```

## 2. เปิดช้า — ยิง Google Sheets 569 ครั้งต่อการเปิดหน้าเดียว

### สาเหตุ

`readAll_()` ยิงชีตใหม่ทุกครั้งที่ถูกเรียก และไม่มีแคชระดับคำขอเลย
ตัวที่ทำให้ระเบิดคือ **`TZ_()` → `getConfig_()` → `readAll_(Config)` ถูกเรียก "ต่อแถว"**
ในลูปคิดแต้ม (`dateStrOf_`, `approvedCountOn_`) — งาน 200 ชิ้น = อ่านชีต 200 ครั้ง
เพื่อถามแค่ว่าเขตเวลาคืออะไร

ซ้ำด้วย N+1: `findById_()` ถูกเรียกในลูป map (`mapSubmission_` หาชื่องานทีละแถว)

### ที่แก้

แคชระดับ "การรันหนึ่งครั้ง" ใน `Db.gs` — ตัวแปรระดับสคริปต์ของ Apps Script
รีเซ็ตทุกคำขออยู่แล้ว จึงไม่มีทางค้างข้ามคำขอ:

- `SS_CACHE_` / `SHEET_CACHE_` — ไม่ `openById` ซ้ำ
- `ROWS_CACHE_` — `readAll_` ต่อ tab ครั้งเดียวต่อรอบ
- `BYID_CACHE_` — `findById_` เป็นการค้นแบบดัชนี ไม่ใช่สแกนทีละแถว
- `CFG_CACHE_` — `getConfig_` ครั้งเดียวต่อรอบ
- `invalidate_(tab)` เรียกทุกจุดที่เขียนชีต: `insert_` / `update_` / `remove_` /
  `setConfigMany_` / `pruneSessions_` / `logout_` / `repairSheetTypes`
- `ensureRepaired_()` เช็ค properties ครั้งเดียวต่อรอบ (เดิม batch 10 รายการ = ถาม 10 ครั้ง)

### ผล (วัดด้วย stub ของ SpreadsheetApp · ข้อมูล: เด็ก 3 คน, งานสะสม 200 ชิ้น, รอตรวจ 20 ชิ้น)

| หน้าจอ | ก่อน | หลัง | |
|---|---:|---:|---|
| หน้าหลักเด็ก (`child.state` + `child.leaderboard`) | 569 | 6 | 95× |
| หน้าสถานะงานของเด็ก | 75 | 2 | 38× |
| หน้าตรวจงานผู้ปกครอง | 125 | 7 | 18× |
| หน้าแต้มของผู้ปกครอง | 8 | 5 | 2× |

569 ครั้ง × ~40 ms ≈ 23 วินาที ซึ่งชนเพดาน timeout ฝั่ง frontend (25 วินาที) พอดี —
อธิบายทั้งอาการ "เปิดช้า" และ "เชื่อมต่อนานเกินไป" ที่โผล่เป็นครั้งคราว

**⚠️ กฎที่ต้องรักษาต่อไป:** object ที่ `readAll_`/`getConfig_` คืนมาใช้ร่วมกันทั้งรอบ
**ห้ามแก้ค่าในนั้นตรงๆ** ถ้าจะเปลี่ยนข้อมูลให้ผ่าน `update_()` หรือ `Object.assign({}, row, patch)`
และถ้าเขียนชีตตรงๆ โดยไม่ผ่าน DAL ต้องเรียก `invalidate_()` เองเสมอ

## 3. สิ่งที่เปลี่ยนไปหลัง deploy (คาดไว้ ไม่ใช่บั๊ก)

- **เลเวลเด็กจะกระโดดขึ้น** เพราะโบนัสภารกิจ/บอสที่เคยตกหล่นถูกนับเป็น XP ย้อนหลังทั้งหมด
  (เด็กจะเห็นฉากฉลองขึ้นเลเวลตอนเปิดแอปครั้งแรก)
- **ดาเมจบอสเดือนนี้จะเพิ่มขึ้น** เพราะโบนัสภารกิจประจำวันถูกนับเข้าดาเมจ อาจล้มบอสทันที
- งานที่อนุมัติไปก่อนมีคอลัมน์ `awards` ยังคงถอยไปใช้ `pointsPerPerson` (ยอดก่อนโบนัสสตรีค)
  ตามเดิม — ข้อมูลเก่าไม่มีรายละเอียดพอจะคิดย้อนหลังได้

## 4. ความเสี่ยงที่ยอมรับไว้

การสลับให้ปั๊มสถานะ "ผ่าน" ก่อนแจกแต้ม เปลี่ยนโหมดพังกรณีสคริปต์ตายกลางคัน:
เดิม = แต้มออกแล้วแต่งานยังค้าง "รอตรวจ" (อนุมัติซ้ำได้ = จ่ายซ้ำ)
ใหม่ = งานขึ้น "ผ่าน" แล้วแต่บางคนอาจยังไม่ได้แต้ม (อนุมัติซ้ำไม่ได้ ต้องปรับแต้มด้วยมือ)
เลือกแบบใหม่เพราะ **จ่ายขาดแก้ได้ จ่ายซ้ำแก้ยาก** — และชีตไม่มี transaction อยู่แล้ว
