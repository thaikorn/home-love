## 1. ทำไมยังช้าอยู่

การเรียก Apps Script หนึ่งครั้งไม่ได้เสียเวลาแค่ตอนอ่านชีต — มันคือ **การรันสคริปต์ใหม่ทั้งรอบ**
(บูตสคริปต์ + ตรวจ session + อ่านชีต) ประมาณ 1–2 วินาทีต่อครั้ง และคำขอของผู้ใช้คนเดียวกัน
**ถูกจัดคิวให้รันทีละอัน** ยิงพร้อมกันสองอันจึงไม่ได้เร็วขึ้น แต่กลายเป็นรอสองรอบต่อกัน

การเปิดแอปของเด็กเดิมเป็นแบบนี้:

```
โหลดหน้าเว็บ (bundle 225KB) ──► parse + mount React ──► auth.me ──► child.counts
                                                                  └► child.state + child.leaderboard
```

- `auth.me` **บล็อกทุกอย่าง** ทั้งที่ได้กลับมาแค่ชื่อกับบทบาท — ยังไม่รู้ด้วยซ้ำว่าจะโหลดอะไรต่อ
- แล้วหน้าจอถึงค่อยยิงข้อมูลจริงอีกสองคำขอ (ตัวเลขบนเมนู กับข้อมูลของแท็บ) ซึ่งวิ่งต่อคิวกันอีก
- ช่วงที่มือถือกำลัง parse + mount React เน็ตว่างเปล่า ไม่ได้ทำอะไรเลย

รวมแล้ว **3 รอบต่อกัน** กว่าเด็กจะเห็นแต้มตัวเอง และทุกหน้าจอก็เป็นแบบนี้เหมือนกันหมด
(ทุกแท็บยิงอย่างน้อยสองคำขอตอนเปิด)

## 2. ที่แก้

### 2.1 รวมคำขอที่ยิงในจังหวะเดียวกันให้เหลือรอบเดียว (`api.js`)

`call()` ไม่ได้ยิงทันทีอีกต่อไป แต่เข้าคิว 12 มิลลิวินาที แล้วส่งทุกตัวที่อยู่ในคิวไปเป็น
`batch` เดียว (ท่า `batch` มีอยู่แล้วในหลังบ้าน แค่ไม่เคยถูกใช้อัตโนมัติ)

- **ไม่ต้องแก้หน้าจอไหนเลย** — `child.counts` ของแถบเมนู กับข้อมูลของแท็บ ไหลมารวมกันเอง
- `callBatch()` เดิมก็ปล่อยเข้าคิวเดียวกัน จึงรวมกับ `call()` ตัวอื่นได้ด้วย
- เกิน 10 รายการแตกเป็นรอบถัดไปให้เอง (เพดานฝั่ง `dispatch_`)
- รายการที่ล้ม **ล้มเฉพาะตัวมัน** ตัวอื่นในรอบเดียวกันยังได้ข้อมูลตามปกติ
- `auth.loginChild` / `auth.loginParent` / `auth.logout` ไม่ถูกรวม เพราะเปลี่ยน token ระหว่างทาง
  (หนึ่ง batch ใช้ token เดียว)

### 2.2 ไม่ต้องรอ `auth.me` ก่อนเข้าแอป (`App.jsx`)

จำ `{role, refId, name}` ล่าสุดไว้ใน localStorage คู่กับ token → เปิดแอปเข้าหน้าจริงได้เลย
แล้วยิง `auth.me` ตามไปตรวจแบบไม่บล็อกหน้าจอ (ซึ่งไปรวมอยู่ใน batch เดียวกับข้อมูลหน้าแรกพอดี
จึงไม่เสียคำขอเพิ่มเลย) token เสีย/หมดอายุเมื่อไหร่ก็เด้งกลับหน้าล็อกอินตอนนั้น

**เน็ตสะดุดแล้ว `auth.me` ล้ม ทั้งที่มี session เก่าอยู่ → ไม่เตะออก** ให้ใช้หน้าเดิมต่อ
(เดิมล้มเมื่อไหร่คือลบ token ทิ้งทันที ต้องใส่ PIN ใหม่)

### 2.3 เริ่มยิงข้อมูลตั้งแต่ยังโหลด JS ไม่เสร็จ (`Code.gs` + `api.js`)

`servePage_()` ฝังสคริปต์เล็กๆ (~10 บรรทัด) ไว้ต้น `<head>` ให้ยิง action ใหม่ `boot`
ทันทีที่หน้าเปิด — **ก่อน** ที่มือถือจะ parse bundle 225KB เสร็จด้วยซ้ำ

`boot` ดูบทบาทจาก token แล้วส่งข้อมูลชุดแรกของหน้าจอนั้นมาให้ครบในรอบเดียว:

| สถานะ | ส่งมาให้ |
|---|---|
| เด็ก | `auth.me` + `child.counts` + `child.state` + `child.leaderboard` |
| ผู้ปกครอง | `auth.me` + `parent.counts` + `parent.reviewQueue` |
| ยังไม่ล็อกอิน | `auth.me` (null) + `auth.childList` — หน้าเลือกเด็กขึ้นทันที |

ฝั่ง `api.js` `call()` ตัวแรกของแต่ละ action จะไป **กิน promise นั้นแทนการยิงใหม่**
(กินได้ครั้งเดียว — เรียกซ้ำ/กลับมาดูหน้าจอใหม่ ต้องไปเอาของสดเสมอ ไม่งั้นจะค้างข้อมูลเก่า)

หลังบ้านตัดสินใจเองว่าจะส่งอะไรมาตามบทบาท สคริปต์ที่ฝังไว้จึงไม่ต้องรู้เรื่องหน้าจอเลย
และ **ห้ามทำให้หน้าพัง** — ยิงไม่ทัน / ล้ม / `localStorage` ใช้ไม่ได้ / ไม่มี action ที่ขอ
ก็แค่ถอยไปยิงเองตามปกติ

### 2.4 เขียนชีตเป็นช่วง ไม่ใช่ทีละช่อง (`Db.gs`)

`update_()` เดิมยิง `setValue()` **ทีละฟิลด์** — อนุมัติงานหนึ่งชิ้นเขียน 5 ฟิลด์ = ยิง 5 ครั้ง
ตอนนี้รวมคอลัมน์ที่ติดกันเป็นช่วงแล้วเขียนครั้งเดียวต่อช่วง (`colRuns_`)
ช่องที่ไม่ได้สั่งแก้ไม่ถูกแตะเลย · `insert_` และ `setConfigMany_` ก็รวบแบบเดียวกัน
(หน้าตั้งค่าส่งมาทีเดียว 20 คีย์ = เดิมยิง 40 ครั้ง)

### 2.5 เลิก "เขียนแล้วทิ้งแคช แล้วอ่านใหม่ทั้งใบ" (`Db.gs`)

เดิมทุกการเขียนเรียก `invalidate_()` ทิ้งแคชทั้ง tab การอ่านครั้งถัดไปจึงต้องดึงชีตใหม่หมด
อนุมัติงานทีมสามคน = เขียน `Children` 6 ครั้ง → **ดึงตาราง `Children` ใหม่ทั้งใบ 9 ครั้ง
ในคำขอเดียว**

`update_`/`insert_` รู้อยู่แล้วว่าตัวเองเปลี่ยนอะไร จึงแก้แถวในแคชให้ตรงกับที่เขียนลงชีตไปเลย
ค่าที่ได้เท่ากับการอ่านกลับมาใหม่ทุกประการ (มีเทสต์เทียบให้ — ข้อ 4)
`remove_` ยังทิ้งแคชเหมือนเดิม เพราะลบแถวแล้วเลขแถวของทุกแถวถัดลงไปเลื่อนหมด

นอกจากนี้ `getDataRange()` คลุมถึงแถว/คอลัมน์สุดท้ายที่มีข้อมูลพอดีอยู่แล้ว จึงเก็บ
**หัวตารางกับจำนวนแถว** ไว้ตั้งแต่ตอนอ่าน — `ensureCols_()` กับ `insert_()` ไม่ต้องยิงถาม
`getMaxColumns` / `getRange(หัวตาราง)` / `getLastRow` ซ้ำอีก

## 4. เทสต์ที่ใช้ยืนยัน

รันบน stub ของ Apps Script (`SpreadsheetApp` / `CacheService` / `LockService` / `Utilities`)
ที่นับจำนวน round-trip ไปด้วย

1. **เทสต์เชิงเปรียบเทียบ** — รันงานเดียวกันบนโค้ดเก่า (HEAD) กับโค้ดใหม่ แล้วเทียบทั้ง
   **ค่าที่ action คืนกลับ** และ **เนื้อชีตทั้งใบ** ว่าเหมือนกันเป๊ะ · 12 สถานการณ์
   (อนุมัติเดี่ยว/ทีม/ติดกัน 5 ชิ้น, ตีกลับ, ปรับแต้ม, แลกของแล้วปฏิเสธ, ซื้อโล่,
   อธิษฐาน→แปลงเป็นรางวัล, บันทึกตั้งค่า, สร้าง/แก้/ลบเด็ก, อ่านทุกหน้าจอทั้งสองฝั่ง) — **ผ่านหมด**
2. **ความถูกต้องของ `Db.gs`** — `update_` เขียนถูกช่องทั้งกรณีช่วงติดกันและช่วงที่ขาด,
   ไม่แตะช่องที่ไม่ได้สั่งแก้, `setConfigMany_` ไม่แตะคีย์อื่นที่คร่อมอยู่ในช่วงที่เขียน
3. **ตัวรวมคำขอใน `api.js`** — รวมถูก, แตกรอบเมื่อเกิน 10, รายการที่ล้มไม่ลากตัวอื่นล้มด้วย,
   login/logout ไม่ถูกรวม, prefetch กินได้ครั้งเดียว, ล็อกอินใหม่ไม่ได้ข้อมูลของคนเก่า
4. **สคริปต์ที่ฝังในหน้าเว็บ** — รันจริงในแซนด์บ็อกซ์: ยิงถูก URL/รูปแบบ, ไม่มี `</script>`
   ค้างในสตริง, ไม่มี `__API_URL__` / `localStorage` ใช้ไม่ได้ / backend ตอบ `ok:false`
   → เงียบและถอยให้แอปยิงเอง

## 5. กฎที่ต้องรักษาต่อไป

- **ห้ามแก้ค่าใน object ที่ `readAll_`/`findById_` คืนมาโดยตรง** (กฎเดิม แต่ตอนนี้สำคัญกว่าเดิม
  เพราะแคชไม่ถูกทิ้งหลังเขียนแล้ว) — จะเปลี่ยนข้อมูลต้องผ่าน `update_()` เท่านั้น
  ถ้าเขียนชีตตรงๆ โดยไม่ผ่าน DAL ต้องเรียก `invalidate_()` เองเสมอ
- เพิ่ม action ใหม่ที่หน้าแรกต้องใช้ **ให้ใส่ใน `boot_()` ด้วย** ไม่งั้นมันจะกลายเป็นคำขอที่สองเงียบๆ
- `boot` ส่งเฉพาะ action ที่ทำสำเร็จ — ตัวที่พังถูกตัดออกจาก map แล้วหน้าเว็บยิงเอง
  จึงไม่มีทางที่หน้าจอจะค้างเพราะ `boot` พังบางส่วน

## 6. ที่ยังไม่ได้ทำ (ถ้าอยากเร็วกว่านี้อีก)

- **bundle 225KB (gzip 68KB)** — React + ReactDOM กินไปเกือบครึ่ง สลับไป Preact ผ่าน alias
  น่าจะเหลือราวครึ่งเดียว แต่ต้องไล่เทสต์ใหม่ทั้งแอป
- **แคชข้อมูลชีตข้ามคำขอ** (`CacheService`) — ตัดการอ่านชีตได้เกือบหมดในคำขอที่ต่อเนื่องกัน
  แต่ถ้าผู้ปกครองไปแก้ชีตด้วยมือ แอปจะเห็นค่าเก่า — ยังไม่คุ้มความสับสน
